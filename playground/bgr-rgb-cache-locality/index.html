The Reversal That Wasn't Free

A one-line NumPy slice was quietly costing us milliseconds on every frame in a real-time detection pipeline. Guess the bug before I show you.

The setup

Our vision pipeline reads frames in OpenCV's native BGR channel order, but the detection model expects RGB. The obvious one-liner flips the channel axis with NumPy:

preprocessing.pynumpy
# reorder channels before handing the frame to the model
rgb = bgr_frame[:, :, ::-1]

NumPy doesn't touch a single byte here — no allocation, no copy, just a new view with a negative stride on the channel axis. By the usual definition of "free," this should be as cheap as an operation gets.

So — what actually happens when the rest of the pipeline touches rgb?

slower — here's why

Every later step that walks this array — resizing, the copy into pinned memory for the GPU transfer — expects a flat, contiguous block it can process in wide chunks. A negative-stride view isn't that. It's still "one array" logically, but physically the elements a routine expects to find next to each other are laid out backwards. Optimized, vectorized code can't take its fast path on that; it falls back to walking the array one element at a time.

preprocessing.pyopencv
# writes a fresh, contiguous, vectorized copy
rgb = cv2.cvtColor(bgr_frame, cv2.COLOR_BGR2RGB)

cv2.cvtColor does strictly more work on paper — it actually allocates and writes a new array — but does it with SIMD-optimized C++ that moves memory in contiguous chunks. Doing more work in a shape the CPU likes beat doing "no work" in a shape it doesn't.
